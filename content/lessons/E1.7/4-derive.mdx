The Explore phase found the rules Python follows when it reads an attribute, compares two objects and works out an operator. Now reason from them: prove what a program prints, find what a tolerance does to `==`, and count, then weigh, the objects that an expression leaves behind.

## Reading and assigning, line by line

Here is a class with two attributes in its body, a count and a list, and a method that uses both:

```python
class Run:
    count = 0
    losses = []

    def log(self, loss):
        self.count = self.count + 1
        self.losses.append(loss)

a = Run()
b = Run()
a.log(0.9)
a.log(0.7)
print(a.count, Run.count, b.losses)
```

It prints `2 0 [0.9, 0.7]`: the count grows on `a` alone, while the list grows for every run, `b` included.

<Reveal for="derive-lookup-proof">

The two lines of `log` look alike, but `self.count = self.count + 1` assigns through `self`, which always gives the object an attribute of its own, while `self.losses.append(loss)` changes, in place, a list that it found through `self`. So a class's body is the place for values that every instance may share and none changes, such as `Double`'s `name` in the Explore phase, while anything that each instance changes belongs in `__init__`, as `self.losses = []`. A count of every run's calls, kept for the whole class, has to be assigned through the class itself, as in `Run.count = Run.count + 1`.

## Equal within a tolerance

E1.1 found that two floats that should be equal may differ in their last digits, so a program should ask whether they are within a tolerance. A config's `__eq__` might do the same, with `t` a small number, such as $10^{-9}$, set before the class:

```python
    def __eq__(self, other):
        return abs(self.lr - other.lr) <= t and self.batch == other.batch
```

Equality of numbers passes along a chain: if $x = y$ and $y = z$, then $x = z$. Does this `==`? Take three configs `a`, `b` and `c` with the same batch size, and write $x$, $y$ and $z$ for their learning rates. Suppose that `a == b` and `b == c` are both `True`.

So this `==` does not pass along a chain: with $y = 0.1$, $x = 0.1 - t$ and $z = 0.1 + t$, `a == b` and `b == c` are `True`, yet `a == c` is `False`. The search notices: whether a config is skipped can depend on which configs were tried before it. Take three configs at the learning rates $0.1$, $0.1 + 0.8t$ and $0.1 + 1.6t$. Tried in that order, the second is skipped as equal to the first, and the third, $1.6t$ from the first, is trained: two configs. Tried with the middle one first, it makes both of the others equal to a config already tried: one config. Settings that people write, such as 0.01, give the same float every time they are written, so plain `==` suits them, and a tolerance belongs where a computed float is checked, as in E1.1's tests.

## The objects an expression leaves

The Explore phase's `Num` made a new object for every `+` and `*`. Suppose that each object made by a class like it also keeps a list of the two values it was made from, its *parents*. Call the class `Value`: `Value(2) * Value(3)` gives a new value holding 6, whose `parents` is a list of the two values that were multiplied, and `Value(0)` is a value with no parents. The Build phase writes this class, the beginning of the autograd engine that L3.4 builds.

A neuron works out a weighted sum of its inputs, $w_1 x_1 + w_2 x_2 + \dots + w_n x_n$. With the weights and the inputs kept as `Value`s in two lists, `w` and `x`, each of length `n`, a loop can build the sum:

```python
total = Value(0)
for i in range(n):
    total = total + w[i] * x[i]
```

Each value keeps its parents, so `total` holds on to the last sum, which holds on to the sum before it and to the last product, and so on down to the weights and the inputs. The loop's whole tree stays in memory for as long as `total` does: $2n$ new values on top of the $2n$ weights and inputs and the starting zero. Read backwards, from `total` to the weights, that tree is what M6.5 calls a computational graph, and L3.4's backward pass follows the `parents` of each value to find how the result depends on every weight.

## What a graph of objects weighs

On the 64-bit machines that train models, a `Value` made by `+` or `*` takes about 90 bytes for the object and its two attributes, 24 for its float and 72 for its list of two parents: close to 200 bytes in all. A language model with $7 \times 10^9$ weights does almost all of its work in weighted sums like this one, so working out its output for one token takes about one multiplication and one addition for each weight. Suppose that every one of its numbers were a `Value`.

The weights themselves, as `Value`s, would take more than 1,000 GB besides. Kept as plain numbers of 2 bytes each, side by side in one block of memory, the same weights take $7 \times 10^9 \times 2 = 1.4 \times 10^{10}$ bytes, 14 GB, as M1.1 found: about a hundredth of the memory. That is why numerical code never keeps one number in each object. NumPy's arrays and PyTorch's tensors are objects too, but each holds a whole block of plain numbers, and a tensor's `+` and `*` work on all of them at once. So the graph that PyTorch keeps has one node for each operation on a whole tensor, not one for each number. E2.1 looks at how an array lays out its numbers.
