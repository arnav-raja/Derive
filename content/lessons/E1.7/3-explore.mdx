## A new kind of value

E1.1 found that every value has a type, such as int, float, str or bool, and E1.4 added lists, dicts and sets. A value's type decides what the value holds and what can be done with it. A *class* is a new type, written in the program itself. The puzzle's four lines make one, called `Config`:

```python
class Config:
    def __init__(self, lr, batch):
        self.lr = lr
        self.batch = batch
```

The line `class Config:` begins the class, and the lines indented below it are its *body*. The body holds a function named `__init__`, with two underscores before `init` and two after it. Calling the class, as in `Config(0.01, 32)`, does three things in turn:

1. Python makes a new object of the type `Config`, with nothing in it yet.
2. It calls `__init__`, with `self` referring to that new object, followed by the arguments of the call: `lr` refers to 0.01 and `batch` to 32.
3. The call gives back the new object.

An object made by a class is an *instance* of the class, so after `a = Config(0.01, 32)`, `a` refers to an instance of `Config`. A name written after an object and a dot, as in `self.lr`, is an *attribute* of that object: a name kept in the object itself. The line `self.lr = lr` gives the new object an attribute `lr` and makes it refer to the value of the parameter `lr`, 0.01. The parameter is a local name of the call, gone when the call ends, as in E1.3, but the attribute stays with the object. Outside the class, the object is reached through a name for it, so `a.lr` reads its attribute and `a.lr = 0.1` sets it.

`__init__` has no `return`, so by E1.3 its call gives `None`. That does no harm, since the value of `Config(0.01, 32)` is not what `__init__` returns: it is the object that Python made in the first step, before `__init__` ran. The job of `__init__` is only to give that object its attributes. A class with no `__init__` skips the second step, so calling it makes an object with no attributes of its own, and the call takes no arguments.

```python
a = Config(0.01, 32)
b = Config(0.1, 64)
a.momentum = 0.9
print(a.momentum, b.momentum)
```

Each instance keeps attributes of its own, and assigning an attribute that an object does not have yet gives it one, to that object alone. Reading an attribute that Python cannot find stops it with `AttributeError`, as a missing key stops a dict lookup with `KeyError`. So a misspelt name that is read, such as `a.Lr`, is caught at once, while a misspelt assignment, `a.Lr = 0.1`, quietly gives the object a new attribute and leaves `a.lr` as it was.

## Methods

A function written in a class's body is a *method* of the class, as `append` is a method of lists. Here is a class whose objects keep the mean of the losses given to them, as a training loop's logger does:

```python
class Meter:
    def __init__(self):
        self.total = 0
        self.count = 0

    def add(self, loss):
        self.total = self.total + loss
        self.count = self.count + 1

    def mean(self):
        return self.total / self.count

m = Meter()
m.add(3)
m.add(5)
print(m.mean())
```

`m.add(3)` calls the class's `add`, with `self` referring to the object that `m` refers to, and `loss` referring to 3. It is the same call as `Meter.add(m, 3)`: Python finds `add` in the class of `m`'s object, and passes the object itself as the first argument. That is why every method has `self` as its first parameter, and why a call made through an object writes one argument fewer. The name `self` is only a custom, but every Python programmer keeps to it. A method that forgets this changes nothing and stops with no error, so the mistake shows only in the numbers. An object keeps its attributes from one call to the next, and that is how a meter, a model or an optimiser carries its state through training.

## What == asks

Back to the puzzle. `a == b` gave `False` for two configs with the same settings. When a class does not say what `==` means for its objects, Python falls back on the one test it can make for any two objects: whether they are one and the same, the question that `is` asks. The puzzle's two configs were made by two calls, so they are two objects, and `==` said `False`. `in` compares a value with the items of a list by `==`, so it never found a config in `tried`, however equal.

A class says what `==` means for its objects with a method named `__eq__`. Python works out `a == b` as the call `a.__eq__(b)`, with the object on the left as `self` and the one on the right as the other parameter, and the call's value is the answer:

```python
class Config:
    def __init__(self, lr, batch):
        self.lr = lr
        self.batch = batch

    def __eq__(self, other):
        return self.lr == other.lr and self.batch == other.batch

a = Config(0.01, 32)
b = Config(0.01, 32)
```

## What print shows

`print(a)` shows something like `<__main__.Config object at 0x2658880>`: the class's name, and a number that says where in the computer's memory the object is, which changes from run to run. A class says what `print` shows for its objects with a method named `__repr__`, which returns a str:

```python
    def __repr__(self):
        return "Config(" + str(self.lr) + ", " + str(self.batch) + ")"
```

Written in the body of `Config`, it makes `print(a)` show `Config(0.01, 32)`, and `str(a)` give that text as a str. A list shows each of its items with `__repr__`, so `print([a, b])` shows `[Config(0.01, 32), Config(0.01, 32)]`. The custom is to make `__repr__` look like the call that would make an equal object, so that a printout reads like code. (A class can also have a `__str__`, which `print` and `str` use in place of `__repr__` when there is one, but `__repr__` alone serves them and lists alike.) `__repr__` must return its str, not print it. One that prints returns `None`, and then `print(a)` stops with `TypeError: __str__ returned non-string (type NoneType)`. The error names `__str__` because, for a class without a `__str__` of its own, the `__str__` that `print` asks for is Python's own, which calls `__repr__`.

## Operators are methods

`==` is not the only operator a class can take over. Python works out `a + b` as the call `a.__add__(b)`, and `a * b` as `a.__mul__(b)`, with the object on the left as `self` each time. Here is a class whose `+` and `*` print a line when they are called:

```python
class Num:
    def __init__(self, v):
        self.v = v

    def __add__(self, other):
        print("add", self.v, other.v)
        return Num(self.v + other.v)

    def __mul__(self, other):
        print("mul", self.v, other.v)
        return Num(self.v * other.v)

a = Num(2)
b = Num(3)
c = Num(4)
d = a + b * c
print(d.v)
```

</Reveal>

<Reveal for="explore-call-order">

The calls follow the expression's tree, not the order in which the operators are written, and each call made a new `Num` and left `a`, `b` and `c` as they were, as `+` and `*` on numbers do. A PyTorch tensor's `+` and `*` work this way, which is why `y = w * x + b` on tensors reads just as it does on numbers.

The object on the left decides: `a * 2` calls `a.__mul__(2)`, whose `other.v` would fail, since an int has no attribute `v`. And `2 * a` first tries the int's own `*`, which knows nothing of `Num`, so Python stops with `TypeError: unsupported operand type(s) for *: 'int' and 'Num'`, unless `Num` has a method `__rmul__`, which Python tries next, with the object on the right as `self`.

## A class built on another

A class can be built on another. `class Sub(Base):` makes `Sub` a *subclass* of `Base`, which is its *base*, and reading an attribute looks in the object, then in its class, then in its class's base, and takes the first it finds. So a subclass has every method of its base, unless it has one of the same name, which then comes first:

```python
class Base:
    def greet(self):
        return "hello"

    def kind(self):
        return "base"

class Sub(Base):
    def kind(self):
        return "sub"

s = Sub()
print(s.greet(), s.kind())
```

This prints `hello sub`: `greet` is found in `Base`, and `kind` in `Sub`, before the one in `Base`.

One more special method: Python works out `f(x)`, for an object `f` that is not a function, as the call `f.__call__(x)`, so an object can be called like a function. Here a base class `Layer` has a `__call__`, and two subclasses each have a name and a method `forward` of their own:

```python
class Layer:
    def __call__(self, x):
        print("calling", self.name)
        return self.forward(x)

class Double(Layer):
    name = "double"

    def forward(self, x):
        return 2 * x

class AddOne(Layer):
    name = "add one"

    def forward(self, x):
        return x + 1

f = Double()
g = AddOne()
print(g(f(5)))
```

Inside `Layer`'s `__call__`, `self` refers to a `Double` or an `AddOne`, so `self.name` and `self.forward` are looked up from the object's own class, not from `Layer`, where the method was written. That is how one `__call__` serves every kind of layer, each with its own `forward`. Every layer of a PyTorch model is built in just this way, on a base class called `Module`, whose `__call__` does some bookkeeping and then runs the layer's own `forward`. And `g(f(5))` runs `f` first, as M1.3's composition does: a list of layers applied in turn is a composition of them, which the Build phase turns into a class.

## The names

<Definition term="Class and instance">

A *class* is a new type of value. Calling it, as in `Config(0.01, 32)`, makes a new object of that type, an *instance*, runs the class's `__init__` with `self` referring to the new object, and gives back the object. `__init__` itself must return `None`, and returning anything else stops Python with `TypeError`. An *attribute* is a name kept in an object: `a.lr` reads it and `a.lr = 0.1` sets it, each instance keeps attributes of its own, and reading one that neither the object nor its class has stops Python with `AttributeError`. Names refer to objects as they refer to lists, so after `b = a` a change made through `b` shows through `a`.

</Definition>

<Definition term="Method and self">

A *method* is a function written in a class's body. `m.add(3)` is the call `Meter.add(m, 3)`: the method's first parameter, `self`, refers to the object it was called through. A method changes its object only by assigning through `self`, since a name it assigns without `self.` is local to the call, and an object keeps its attributes from one call to the next.

</Definition>

<Definition term="Special methods">

Python itself calls the methods named with two underscores on each side, when it meets its own syntax: `a == b` calls `a.__eq__(b)`, `print(a)` shows what `__repr__` returns, `a + b` calls `a.__add__(b)`, `a * b` calls `a.__mul__(b)`, and `f(x)` calls `f.__call__(x)`. Without `__eq__`, `==` asks whether two names refer to the same object, as `is` does. An expression with several operators makes its calls in the order of its tree.

</Definition>

<Definition term="Looking up an attribute">

Reading `obj.name` looks among the object's own attributes, then in its class, then in the class's *base*, the class it is built on, and takes the first it finds. Assigning `obj.name = v` always gives the object an attribute of its own. So a list kept in a class is shared by every instance that reads it, a *subclass* can replace a method of its base, and a lookup through `self` starts from the object's own class, wherever the method was written.

</Definition>
