Everything that a call of `step` needs from the calls before it, the best loss so far and the count since it, lives on the object, so two watchers kept for two runs never mix their counts. ## A faster search

<Exercise id="build-break-hash" />

</Reveal>

<Reveal for="build-break-hash">

A set works out where to look for a value from a number that the value's method `__hash__` gives, and two equal values must give the same number, or the set would look for one of them in the wrong place. A class without `__eq__` gets a `__hash__` worked out from the object itself, which suits an `==` that asks whether two objects are one. Once a class defines `__eq__`, that `__hash__` no longer agrees with it, so Python takes it away, and the class's objects can go in no set and be no key of a dict: an error is better than a set that quietly holds two equal configs. A class can give its objects a `__hash__` of its own that agrees with its `__eq__`, and E1.10, on hashing, shows how such a method is made. Until then a list keeps the search right, and for a few hundred configs it is quick enough.

## A sum that changes its inputs

<Exercise id="debug-vec-add" />

</Reveal>

<Reveal for="debug-vec-add">

`return self` handed back the left vector itself, changed. An operator that makes a new value should leave its inputs alone, as `+` on numbers does, since code such as `w = u + v` goes on to use `u`. Python keeps separate operators for changing a value in place: `u += v` calls `u.__iadd__(v)` when the class has that method, and PyTorch marks its methods that change a tensor in place, such as `add_`, with an underscore at the end.
