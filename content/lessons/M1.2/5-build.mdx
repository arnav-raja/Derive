## Python reads trees too

Python follows the same order of operations as paper, so every line of Python has a tree:

- `**` is a power and is done first, then `*` and `/`, then `+` and `-`;
- a chain of `+` and `-`, or of `*` and `/`, is worked from the left;
- brackets change the shape, just as on paper.

One warning. In Python code a power is written `**`, and `^` means something else entirely, so keep `^` for the answer boxes in Derive, where it does mean a power.

## Break a rule on purpose

Explore's calculator kept three significant figures. Here it is in Python, as a ready-made function called `r`: `r(x)` gives `x` rounded to three significant figures. You do not need to know how it works yet; the next lesson, M1.3, shows how to write your own. For example, `r(1.004)` gives `1.0` and `r(1.008)` gives `1.01`. Python shows `1.0` rather than `1.00` because it drops zeros at the end.

To round after every operation, wrap each operation in `r(...)`. The tree for $(a + b) + c$ has one addition inside another, so its line has one call of `r` inside another.

Near 1 the calculator can show 1.00 and 1.01, but nothing in between: its steps there are 0.01 wide, which is why Explore's two groupings differed by 0.01.

Between 1 and 10 the calculator's values go up in steps of 0.01, so an amount smaller than half a step, such as 0.004, is lost when it is added on its own. Near 100 the steps are 1 wide, so the same trick needs amounts about 100 times larger. With $a = 100$ and $b = c = 0.4$, the left grouping loses each 0.4 in turn and stays at 100, while the right grouping adds them first, to 0.8, which pushes $100.8$ up to 101. A real computer's 16 figures fail for the same reason, at a much finer scale, and that is what the puzzle showed.

Explore found that swapping the two numbers of one addition never changes a rounded result. A chain of additions is a different matter: change the order of all three numbers, and see whether the puzzle's `False` survives.

So the order of a chain matters to a computer only through the grouping it produces: which numbers are added first. ## Compare with the library

You have been doing algebra by hand. SymPy, a Python library for algebra with letters, does it by machine, with the same rules. Its `expand` multiplies out every bracket and collects like terms. If the difference of two expressions expands to 0, the rules have turned it into 0, so the two are equivalent.

<Stated>

For expressions built from letters and numbers with $+$, $-$, $\times$ and whole-number powers, which is all you need here, the converse holds too: if the difference does not expand to 0, the two expressions are not equivalent. This rests on a fact not proved here, that such an expression which is not 0 after expanding cannot be 0 for every value of its letters.

`trees` is 0, so $3(x + 4)$ and $3x + 12$ are equivalent. `slip` is $2x$, or $-2x$ if you subtracted the other way round, which is 0 only when $x$ is 0: the slip is wrong for every other $x$. `built` is $x^3 - 3x^2 + 2x$, the product $x(x - 1)(x - 2)$ multiplied out. It is 0 at 0, 1 and 2 and nowhere else, which is exactly the trap from Derive.

What SymPy did was not a check at a few values. It applied distributivity, commutativity and associativity, the same chain of rules you used, until the answer was either 0 or plainly not 0. For harder expressions, with sines or logarithms in them, SymPy has a more ambitious tool, `simplify`, which tries many rules and usually succeeds. Usually is the right word: for expressions built from functions like the sine, it has been proved that no program can settle every equivalence. When `simplify` fails to reach 0, the two expressions may still be equivalent.
