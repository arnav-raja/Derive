## Naming a job

E1.2 counted the halvings that take a rate from 1.0 down to a floor, with the floor written into the loop. A script that needs the count for several floors could copy the loop once for each, but every copy is one more place for a mistake, and a fix made in one copy is easily missed in the others. A function writes the job once:

```python
def halvings(floor):
    lr = 1.0
    count = 0
    while lr > floor:
        lr = lr / 2
        count = count + 1
    return count

print(halvings(0.001))
print(halvings(0.25))
```

The first line is the `def` line. It gives the function's name, `halvings`, and in brackets its *parameter*, `floor`, the name its input will have. It ends with a colon, and the indented lines below it are the function's *body*. Running the `def` line does not run the body. It makes the name `halvings` refer to the function, a value like a number or a string, ready to be run.

The body runs only when the function is *called*, as in `halvings(0.001)`. A call works in four moves:

1. Python works out the *argument*, the value in the brackets, here 0.001.
2. It makes the parameter `floor` a new name for that value.
3. It runs the body from the top.
4. At `return count`, the call ends, and its value is the value of `count`.

That value takes the call's place in the line that made the call, so `print(halvings(0.001))` prints 10, and the next line prints 2, since two halvings take 1.0 to 0.25. A call is an expression, like `2 * x`, so its value can be printed, given a name, used in arithmetic or passed to another call.

A function can have several parameters, separated by commas, and a call gives one argument for each, matched in order: with `def area(width, height):`, the call `area(2, 3)` makes `width` 2 and `height` 3. A function with no parameters has empty brackets, and so does every call of it, as with `input()`. Here is a function that prints as well as returning a value:

```python
def shout(word):
    print(word)
    return 2

print("start")
a = shout("one")
b = shout("two")
print(a + b)
```

<Exercise id="explore-def-runs" />

<Reveal for="explore-def-runs">

Each call runs the whole body again, so `one` and `two` are printed by the two calls, in the order the calls run. The value of a call is what its `return` gives, 2 each time, not what it printed, so `a + b` is 4.

## Printing is not returning

```python
def area(width, height):
    print(width * height)

total = area(2, 3) + area(4, 5)
print(total)
```

<Exercise id="explore-print-not-return" />

</Reveal>

<Reveal for="explore-print-not-return">

A function that ends without reaching a `return` still gives back a value: `None`, the only value of its own type, `NoneType`, which stands for no value at all. So each call of `area` prints its area and gives back `None`, and `None + None` stops Python with a `TypeError`. `print` shows a value to the person running the program, while `return` hands it to the line that made the call. A function whose result the program needs must return it, and the caller can print it if a person needs to see it.

`return` also ends the call at once, wherever it is. So a function can have several, and only the first one reached runs:

```python
def sign(x):
    if x > 0:
        return 1
    if x < 0:
        return -1
    return 0

print(sign(-4) + sign(0) + sign(9))
```

<Exercise id="explore-early-return" />

</Reveal>

<Reveal for="explore-early-return">

`sign(-4)` finds `-4 > 0` `False` and `-4 < 0` `True`, so it returns $-1$, and its last line never runs. `sign(0)` finds both tests `False` and reaches `return 0`. Returning from inside an `if` is a common way to write a chain of cases: once a case has returned, the rest of the function is skipped, so no `elif` is needed.

When the call starts, its parameter `lr` is a new name, belonging to the call alone, for the argument's value, 0.1. `lr = lr / 2` makes that name refer to 0.05, as E1.1's assignments do: it changes the name on its left and no other. The main program's `lr` is a different name that happens to be spelled the same, and nothing assigns it again, so it still refers to 0.1. When the call returns, its names are gone. All that comes back is the value after `return`, 0.05, and the main program makes `smaller` refer to it.

The names that belong to a call are *local* to it: its parameters, and every name that its body assigns. They are made afresh each time the function is called, and are gone when the call returns. The main program's names are *global*.

```python
def warmup_lr(step):
    fraction = step / 1000
    return 0.001 * fraction

lr = warmup_lr(250)
print(fraction)
```

</Reveal>

<Reveal for="explore-local-gone">

`fraction` was local to the call: it was made when the call ran its first line, and it was gone once the call returned. The main program never had a name `fraction`, so Python stops at the last line with `NameError`. Only the value after `return` leaves a call.

## Names from outside

A function can also use a name that it never assigns. Python then looks the name up among the main program's names, and it looks when the call runs, not when the function is defined.

```python
scale = 2

def scaled(x):
    return scale * x

a = scaled(10)
scale = 3
b = scaled(10)
print(a, b)
```

<Exercise id="explore-global-read" />

</Reveal>

<Reveal for="explore-global-read">

The first call finds `scale` referring to 2, and the second finds it referring to 3. So the same call, `scaled(10)`, gives 20 the first time and 30 the second. Keep that in mind: it comes back when we ask which Python functions behave like M1.3's.

Reading a global name is allowed. Assigning one from inside a function is another matter:

```python
count = 0

def tick():
    count = count + 1
    return count

tick()
```

<Exercise id="explore-assign-makes-local" />

</Reveal>

<Reveal for="explore-assign-makes-local">

Python decides which names are local before a call runs: a name that a function assigns anywhere is local throughout it. So in `count = count + 1`, the right side asks for the call's own `count`, which has no value yet, and Python stops with `UnboundLocalError`, its error for a local name used before it has been given a value. The main program's `count` is never touched.

Python can be told otherwise. The line `global count` at the top of the body makes `count`, in that function, the main program's name. It works, but a function that changes the main program's names is much harder to reason about, as the next section shows. The usual cure is to pass the value in and return the new one: `def tick(count):`, with `return count + 1` as its body, called as `count = tick(count)`.

## Functions that behave like M1.3's

M1.3 defined a function as a rule that gives each input exactly one output. `scaled` breaks that rule: `scaled(10)` gave 20 and then 30. A Python function behaves like M1.3's only when two things hold: its value depends on nothing but its arguments, and a call changes nothing outside the function. That means it reads no outside name whose value can change, assigns none, prints nothing and reads no input. A function like that is called *pure*.

Pure functions are the easiest to trust. The same call always gives the same value, so a check that passes once passes every time. And once you know that `halvings(0.001)` is 10, every `halvings(0.001)` in a program can be read as 10, wherever and whenever it runs. Here are five functions:

```python
offset = 0.5   # the script changes offset from time to time

def f(x):
    return x * x + 1

def g(x):
    print(x)
    return x

def h(x):
    return x + offset

def k(n):
    total = 0
    for i in range(n):
        total = total + i
    return total

def m(x):
    return x * float(input())
```

<Exercise id="explore-which-pure" />

</Reveal>

<Reveal for="explore-which-pure">

`f` and `k` are pure. `k` assigns `total` and `i`, but they are its own local names, made afresh by every call, so they change nothing outside it, and its value depends only on `n`. `g` gives back its argument, but it also prints, which changes what the person running the program sees. `h` reads `offset`, which the script changes, so `h(1)` can differ from one call to the next, and `m` reads a new line of input at every call.

## Building from functions

A function's caller needs to know what the function does, not how it does it: what it takes, what it gives back, and what must be true of its arguments. That is the function's *contract*. Python code states it in a *docstring*, a string written as the first line of the body, between three quote marks, `"""`, at each end when it runs over several lines. Here are the first lines of a function from a training script, with its body hidden:

```python
def warmup_lr(step, peak, warmup):
    """The learning rate at a step: rising evenly from 0 to peak over the first
    warmup steps, then holding at peak."""
```

<Exercise id="explore-contract" />

</Reveal>

<Reveal for="explore-contract">

Nothing about the body was needed. Using a function through its contract alone is called *abstraction*: the contract stands for the work, and the work stays out of sight. It frees the function as well: its body can be rewritten, faster or clearer, and no caller has to change, provided the contract still holds.

A value fixed inside a function can become a parameter, so that one function serves many cases. That is how E1.2's loop, with its floor written in, became `halvings(floor)`. A parameter can also have a *default*, a value used whenever a call leaves that argument out. And an argument written as `name=value`, a *keyword argument*, goes to the parameter of that name, whatever its position.

```python
def progress(step, warmup=1000):
    return step / warmup

print(progress(500), progress(500, 250), progress(warmup=4000, step=1000))
```

<Exercise id="explore-defaults" />

</Reveal>

<Reveal for="explore-defaults">

`progress(500)` leaves out `warmup`, so `warmup` is 1,000 and the value is 0.5, while `progress(500, 250)` gives `warmup` by position. The last call names both of its arguments, so their order does not matter: `step` is 1,000 and `warmup` is 4,000. Libraries for training models use defaults and keyword arguments everywhere: their functions take many settings, and most calls change only one or two of them, by name.

Functions combine as in M1.3: the value of one call can be the argument of the next. Here are E1.2's gradient clip and a scaling, as functions:

```python
def clip(g):
    if g > 1:
        return 1.0
    if g < -1:
        return -1.0
    return g

def scale(g):
    return 0.5 * g

print(scale(clip(3.0)), clip(scale(3.0)))
```

<Exercise id="explore-compose" />

</Reveal>

<Reveal for="explore-compose">

In `scale(clip(3.0))` the inner call runs first, as in M1.3's $g(f(x))$: `clip(3.0)` is 1.0, and `scale(1.0)` is 0.5. In `clip(scale(3.0))`, `scale(3.0)` is 1.5, and `clip(1.5)` is 1.0. So, as in M1.3, the order of composition matters. Each of these functions does one small job that can be checked on its own, and together they do a larger one. That is how large programs are built: from small functions, each trusted through its contract, combined into larger ones.

## The names

<Definition term="Function">

A *function* is a named block of lines, its *body*, that runs only when the function is called. `def` makes the function's name refer to it, and gives its *parameters*, the names its inputs will have. A *call* works out its *arguments*, makes each parameter a new name for its argument's value, runs the body and ends at the first `return` it reaches. The value after `return` becomes the value of the call. A function that ends without reaching `return` gives `None`. Printing a value shows it to a person; returning it hands it to the program.

</Definition>

<Definition term="Local and global names">

The names a call makes, its parameters and every name its body assigns, are *local* to that call: made when the call starts, gone when it returns, and separate from any name spelled the same outside. The main program's names are *global*. A name that a function uses but never assigns is looked up among the global names as they stand when the call runs. A name that a function assigns anywhere is local throughout it, so using it before it is assigned stops Python with `UnboundLocalError`.

</Definition>

<Definition term="Pure function">

A function is *pure* when its value depends on nothing but its arguments and a call changes nothing outside it: it reads no outside name whose value can change, assigns none, prints nothing and reads no input. A pure function gives the same value whenever it is given the same arguments, as a function in M1.3 does.

</Definition>

<Definition term="Abstraction">

A function's *contract* says what it takes, what it gives back and what must be true of its arguments, often in a *docstring*. *Abstraction* is using a function through its contract alone, without looking at how its body works. Parameters, with *defaults* for their usual values, let one function serve many cases, and functions combine by passing the value of one call as the argument of the next.

</Definition>
