## Sorting by runs

<Exercise id="build-runs" />

<Reveal for="build-runs">

On a list already in order, `run_sort` finds one run in $n - 1$ comparisons and is done, as the puzzle's `sorted` was. On 1,000 shuffled losses it finds about 500 runs, most of them 1 or 2 items long, and makes about 9,350 comparisons in all, more than merge sort's 8,700 or so, since finding the runs costs 999 comparisons and short runs save little. Timsort does better on shuffled lists: a run shorter than a minimum, between 32 and 64 items for a long list, is lengthened by inserting the items after it one at a time, each in the place that a binary search finds for it, which takes few comparisons. It also chooses which neighbouring runs to merge, so that the runs merged are of similar lengths, by a rule called *powersort* since Python 3.11.

For 1,000 shuffled losses, then:

| Sort | Comparisons |
| --- | --- |
| The bound, for any sort that only compares | 8,530 |
| Python's `sorted` (Timsort) | about 8,650 |
| Merge sort | about 8,700, and 8,977 at worst |
| `run_sort` | about 9,350 |
| Picking the smallest left, again and again | 499,500 |

The rule runs one way only: equal keys must have equal hashes, but unequal keys may share one. A `__hash__` that returned 0 for every config would still give right answers, with every config in one bucket, so every lookup would compare with every key, as a search of a list does. A good hash uses every field that `__eq__` compares, so that keys which differ seldom share a bucket.
